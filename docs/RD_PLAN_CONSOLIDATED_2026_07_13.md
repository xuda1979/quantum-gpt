`docs/archive/rd-lines-2026-07-13/`).

---

## Architecture: 13 lines → 2 adapters + 1 auxiliary

The original program had 13 independent R&D lines (10 "N-lines" + base-SFT
+ RL-GRPO + science-Q&A). Each N-line targeted a *single* failure category
(ImportError, prose-only, TypeError, etc.). That architecture is wrong for
deployment: an adapter that fixes only ImportError is useless if it emits
prose-only output. **The failure categories are complementary, not
competing, so all error-fix lines must be merged into one adapter.**

| Adapter | Role | Lines merged | Method | Deploy? |
|---------|------|-------------|--------|---------|
| **A: Quantum-Code (main)** | Fixes ALL coding error categories | base-SFT + N1,N3,N4,N5,N6,N7,N8,N10 + RL-GRPO | SFT curriculum → unified DPO → RL | ✅ primary |
| **B: Quantum-Science Q&A** | General quantum research, non-coding | rl-science-distill plan | SFT → RL | ✅ secondary (separate serving route) |
| **Aux: Quantum-Critic** | Judge model — reward signal for A's RL | N2 (critic) + N9 (selector) | SFT | ❌ not deployed standalone; used at train time |

**Why 2 adapters, not 1:** Coding and science-Q&A have different I/O
contracts (code-with-tests vs. cited prose). Mixing them in one adapter
dilutes both. They serve different user intents and can be routed at
serving time. The critic is a training-time auxiliary, not a deploy target.

## Adapter A — Quantum-Code (the main deliverable)

### Stage 1: SFT curriculum (fixes structural / deterministic errors)

Merges N4 + N5 + N8 into the base distillation SFT set:

| Former line | Error fixed | Data source | Rows |
|-------------|-------------|-------------|-----:|
| N4 OSE-SFT | output-string mismatch | tasks with deterministic stdout | 7 |
| N5 CC-SFT | NameError/SyntaxError in circuit construction | deutsch_jozsa, bernstein_vazirani, bell_pair variants | 10 |
| N8 QCC-SFT | QAOA cut-value wrong | maxcut family + graph variants | 5 |

These are **SFT** (not DPO) because the failure is "model doesn't know the
right pattern" — there's a single correct answer, so supervised learning on
the reference candidate is the right signal.

### Stage 2: Unified DPO (fixes preference / choice errors)

Merges N1 + N3 + N6 + N7 + N10 into **one DPO dataset** with a
`source_line` tag on every pair:

| Former line | negative_type | Data source |
|-------------|---------------|-------------|
| N1 UF-DPO | `assertion` (universal-failure) | 7 tasks failing on all 3 models; ref vs failing roll-out |
| N3 IP-DPO | `import_error` | ref vs import-mutation |
| N6 fmt-DPO | `prose_only` / `no_main` / `no_guard` | canonical vs format-mutation |
| N7 DM-DPO | `type_error_precedence` | ref vs DensityMatrix type-mutation |
| N10 TR-DPO | `traceback_repair` | failing+tb vs ref |

**Why one DPO dataset:** DPO teaches the model *which output is better*.
All 5 negative types are "worse than the reference" — the model should
learn to reject ALL of them, not just one. A unified dataset lets the
adapter learn the shared "preference for correct, executable, well-formed
code" signal across all error categories simultaneously.

Data generated by `scripts/prepare_unified_dpo.py` →
`data/generated/rd_lines_2026_07_13/unified_dpo_pairs.jsonl`.

### Stage 3: RL-GRPO (execution-grounded reward)

The existing `configs/rl/qwen36_35b_a3b_grpo_rlvr_asi1.json` pipeline,
with two upgrades from this reorg:

1. **Critic-LoRA reward source** (from N2): when
   `TeacherConfig.critic_mode = "local_lora"`, the RL grade step uses the
   trained quantum-critic adapter instead of the GLM5.2 teacher API —
   removing the teacher bottleneck and the 403-quota issue.
2. **Eval-gate armed**: `eval_gate.enabled = true` with
   `verdict_path = <NAS>` so training auto-aborts on regression.

## Auxiliary — Quantum-Critic (N2 + N9 merged)

**Merge rationale:** N2 (critic: "is this code correct?") and N9
(self-consistency selector: "which of these K candidates is correct?")
are the **same task** — judging code correctness. One judge model can do
both: given a task spec + a candidate, output pass/fail + scores. N9's
"pick the best of K" is just running the critic on each candidate and
taking the argmax. So we train **one** critic-LoRA, used two ways.

| Former line | Role | Merged into |
|-------------|------|-------------|
| N2 critic-SFT | pass/fail + scores + reasoning | critic-LoRA |
| N9 SCS-SFT | pick best of K candidates | critic-LoRA (argmax over K) |

Data: `data/generated/rd_lines_2026_07_13/n2_critic_sft_rows.jsonl` (66 rows:
58 positive + 8 negative). The selector use-case needs no separate training
data — it's an inference-time aggregation over the critic.

Success metric: ≥ 85% agreement with execution-grounded pass/fail on the
held-out 20% split (`scripts/eval_critic_agreement.py`).
