# Track N10 — Error-Message-Grounded Repair DPO (TR-DPO)

**Owner:** subagent track (loop 2026-07-13, iteration 15:25)
**Status:** design + scaffold
**Target students:** Qwen3.6-27B (ASI1), Qwen3.6-35B-A3B (ASI2/3)
**Constraint:** post-training only; no architecture change.

## Problem

The failure modes in the iter-2 gap report (ImportError, NameError,
TypeError, output mismatch) are all *repairable* — the traceback contains
enough information to fix the bug in one step. But the current pipeline
has no "repair" skill: it generates from scratch and fails the same way
twice. A model that can read a traceback and produce a one-step fix would
close failures that no amount of from-scratch SFT can reach (because the
fix is conditioned on the specific error).

## Approach

Build a DPO pair set where:

- **prompt** = task spec + a failing program + its traceback (the full
  `stderr` from running the program against `tests.py`).
- **chosen** = the corrected program (verified to pass `tests.py`).
- **rejected** = the original failing program unchanged (or a cosmetic
  variant that still fails).

The rejected side is the *exact program that produced the traceback*, so
the DPO signal is corruption-proof: the model learns "given this error,
produce the fix", never "prefer the broken version".

## Data source

- Tasks: the 58-task `evals/tasks/quantum/` directory.
- Failing programs: generated by applying the N1/N3/N7 mutation helpers to
  `candidate.py`, then running `tests.py` to capture the real traceback.
- Fixes: the original `candidate.py` (which passes), reformatted into the
  canonical assistant form.

## Success metric

On a held-out 20% split, a TR-DPO-LoRA adapter must produce a
`tests.py`-passing program **≥ 70% of the time** when given a failing
program + traceback as input (baseline from-scratch = ≤40% on the same
tasks).

## Out of scope

- Any NPU run.
- Modifying the DPO trainer.
- Multi-turn repair (this track is single-step: one traceback → one fix).
