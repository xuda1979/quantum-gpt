## 1. Objectives

Build a serious, rigorous, comprehensive, professional evaluation
harness whose results are **100% trustable**. Motivated by problems
found in the prior review of `evals/`:

1. Reports disagreed with underlying evidence (base status mismarked).
2. Coverage claims were overstated ("495-task holdout" but pass@1 not run).
3. Remote run results could not be locally re-verified at the code level.
4. No mandatory evidence→claim consistency check.

## 2. Method

Design a subsystem where **every reported number is cryptographically
traceable to a reproducible artifact**, and any unbacked claim blocks
publication. Six concrete guarantees:

| # | Guarantee | Mechanism |
|---|---|---|
| 1 | Provenance | SHA-256 hashing + append-only SQLite ledger for every artifact (suite, task, prompt, candidate, verdict, claim) |
| 2 | Reproducibility | Full reproduction recipe (env, git commit, deps, seed, model hash) per run; `reproduce` asserts equality |
| 3 | Hermetic scoring | Per-task sandbox with frozen `PYTHONHASHSEED`, no host site-packages leak, optional network block |
| 4 | Dual verdict | Deterministic program verdict + optional LLM rubric judge; disagreements surfaced, never silently averaged |
| 5 | Evidence→claim auditing | `audit` cross-checks every numeric claim in a human report against the ledger; unbacked claims block publication (exit 1) |
| 6 | Task-suite pinning | `suite.lock.json` pins exact task set + per-task hashes; `verify` detects any post-run edit to `tests.py`/`task.json` |

**Additional requirement (added 2026-07-10)**: all code generated by
base models and adapters during evaluation must be recorded. This is
satisfied by:
- The `sample.candidate_code` column (full text) and
  `sample.candidate_code_hash` (SHA-256) in the ledger.
- On-disk copies at `run_dir/candidates/<task_id>.s<sample_index>.py`.
- A `candidates` CLI subcommand to list, export, and inspect them.

## 4. CLI subcommands

| Command | Purpose |
|---|---|
| `suite-init` | Pin a task suite to a `suite.lock.json` |
| `suite-verify` | Verify a lock against the on-disk task tree |
| `run` | Run a model against a pinned suite (mock / exec / openai / hf) |
| `score` | Re-score a run's samples without regenerating |
| `verify` | Re-check every hash + re-score every sample |
| `audit` | Audit a human report against the ledger |
| `compare` | Compare two runs (base vs adapter) with regression detect |
| `report` | Render an audit-checked Markdown report |
| `reproduce` | Re-run a run from its recipe; assert equality |
| `import-legacy` | Ingest an existing `evals/runs/*/scorecard.json` |
| `candidates` | List / export / show all generated candidate code |

## 7. Decisions log

- **2026-07-10**: Chose SQLite over JSON files for the ledger because
  it gives atomic inserts, foreign keys, and queryability without
  external deps. One `.db` file per run dir.
- **2026-07-10**: Chose subprocess-based hermetic sandbox over
  in-process import, because subprocess isolation prevents host
  site-packages leakage and gives clean stdout/stderr capture.
- **2026-07-10**: Chose to store full candidate code in the ledger
  (not just on disk) so that the ledger is self-contained and can be
  verified without the run dir.
- **2026-07-10**: Chose `--exec-command` as the primary generation
  backend (over in-process HF model loading) because it decouples the
  trust harness from model-loading code and makes generation
  reproducible by anyone with the script.
